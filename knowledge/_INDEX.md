- [[Decisions/2026-08-18 - Sentinel paper execution bound to real TradeW user accounts]] — **read before touching `ExecutionProfile.accountScope`, `User.agentPaperTradingEnabledAt`, or `execution-account.ts`.** An execution profile can now trade an ordinary TradeW user's OWN paper account, and **the integration mechanism is that there is no mechanism**: `/sim/orders` and `/sim/positions` scope by `req.user.sub` against the same `Order`/`Position` tables the console reads, so writing under the user's `userId` means their app shows it *because it is literally the same row* — no sync layer, no mirroring, no frontend change. Additive schema only: `ExecutionAccountScope` defaults **SYSTEM_PAPER** so the pre-existing profile needed no backfill, and consent is a **timestamp** not a boolean (the audit question is *when*, and by whom — same reasoning as `phoneVerifiedAt`). The load-bearing rule: **`accountScope` is a DECLARATION, not a permission** — trusting it leaves two routes to trading a real person's money without consent, so SYSTEM_PAPER additionally requires the account be structurally non-loginable, and USER_PAPER requires consent **re-read every pass** (a cached grant survives its own revocation). No credential anywhere: `passwordHash`/`googleId` collapse to booleans at the query boundary and `eligibleAccounts` never selects them. Two bugs only a REAL account could expose, both fixed: a human's own open position consumed the agent's `maxOpenPositions` budget and deadlocked it (now counted from the profile's own FILLED intents — note the deliberate asymmetry with `maxLossPerDay`, which stays account-wide because it governs shared *capital*), and a policy-REJECTED intent owned its 15-minute idempotency window despite having produced no order (now re-claimed via a status-guarded atomic `updateMany`; an intent that owns an order is never re-claimed). Evidence: `verify:user-binding` 40/40, `verify:paper-execution` 41/41 unchanged before and after, `verify:admin-routes` 11/11. Market was CLOSED — decision recorded, session gate overridden downstream only, both printed; **not** a live-market verification

## Patterns
Reusable engineering patterns, workflow improvements, development standards.
- [[Patterns/2026-08-16 - Selecting a market starts the watch (three charts read, trading days only)]] — **read before touching `market-clock.ts`, `MarketWatchService.isTradingTime`, `CandleMarketDataProvider.getOptionChain`, `MarketIntelligenceService.snapshot`/`contracts`, `SentinelLiveCharts`, or `app/market/clock.py`.** Two halves of one finding — a surface asserting an engine that was not running. **`getOptionChain` returned `[]` for every symbol behind an "honest degradation" comment while the bridge had been serving `/optionchain` the whole time** — so `snapshot.optionChain` was always null, the confidence engine's option factor and the cross-validation option dimension abstained by stub, and `buildOptionContext` reported `unavailable: true` on *every observation ever run*. Now the engine reads the ATM **CE and PE premium series** beside the index (never inferred from the underlying — a call can fall on a rising index, and both legs can rise together when vol is bid; those divergences ARE the observation). Three traps, each pinned: **two flat bands** (0.05% index vs 1.0% premium — one band reports every leg "rising" all day), **"tracking" requires the opposite leg NOT to also rise** (else an IV expansion reads as directional confirmation), and **a leg that could not be read is never a leg that did not move** (`series: null` vs `direction: 'flat'`). The Rule 2 line adopted: naming which leg MOVED with the underlying is description, ranking strikes by attractiveness is a recommendation however worded — so `alignment` is a closed set and **not a score**, it reads ONE pair and says so, and every note is run through `hasDirectiveLanguage`. Also: `SentinelLiveCharts` defaulted to **5m index / 1m contracts while `/observe` has always read 15m**, so a plain market selection had the same chart-vs-engine split the watch focus was built to fix. Half two is **clock unification** — the KNOWN-GAP block in `market-clock.spec.ts` is **inverted, not deleted**, the calendar moved to `@tradew/market-data` (one list for api + sentinel; `discipline/market-calendar.ts` is now a re-export), a non-trading day is **`'closed'` never `'pre-market'`** (PRE_MARKET seeds a session waiting for a bell that will not ring), and the watch's local weekday hack is gone — **the holiday half is what was costing money**, since a holiday is a weekday and every sweep went through. `istMinutesOfDay`/`minutesToClose`/`sessionProgress` stay deliberately day-blind (they size `expiryFor`, they are not gates). **Not driven in a browser; the chain read is only exercised during market hours on a trading day**
- [[Patterns/2026-08-16 - Sentinel reference dashboard band (what the mock asked for that the platform cannot know)]] — **read before adding a panel to `components/sentinel/dashboard/`, wiring a figure into `SessionStats`, or touching `lib/sentinel/sessionTimeline.ts` / `sessionStats.ts`.** A reference screenshot integrated as the band below the reading panel (feed · conditions · radar+emotion → session timeline → stats · actions · context). **Six of the mock's figures had no data source anywhere in TradeW** — FII/DII flow, global breadth, news impact, the forward calendar — and one was outright forbidden (position-size "recommended: 75%" is advice, Rule 2); each would have rendered as a confident constant on every load. ## Gotchas
Debugging discoveries, bug resolutions, lessons learned — things that cost time once and shouldn't cost time twice.
- [[Gotchas/2026-08-18 - Naive timestamps make the Strategy Feed look like it runs outside market hours]] — **read when a UI shows a time that is plausible but wrong, especially if EVERY timestamp is off by the same amount.** Strategy Feed showed events at 06:39/07:04 am — before the 09:15 IST open, on a feed that only fires inside the session — so it read as a broken market clock. It was a **display** bug: every value short by exactly 5h30m, the IST offset. Prisma maps `DateTime` to `timestamp WITHOUT time zone`, asyncpg returns **naive** datetimes, and `.isoformat()` on a naive value emits **no offset**; ECMAScript parses an offset-less string as **local**, so the browser moved the instant back 5h30m and a 12:34 pm event rendered as "07:04 am". Survived review because every part is individually right: the column really holds UTC, `_aware()` already existed but only re-labels for **in-process comparison** (never for JSON), and the frontend formatter already asked for `timeZone: 'Asia/Kolkata'` — it was handed an instant that had already shifted, so asking politely for IST returned the wrong IST. No error, no warning, a valid ISO string, a plausible time. Fix: `app/core/timefmt.py::iso_utc` at all 5 wire sites; it **assumes** naive is UTC rather than `.astimezone()`-ing it, because converting interprets the value in the SERVER's zone and reintroduces the bug only in deployment. **The rule: a datetime crossing a process boundary carries its offset, or it is not a datetime — it is a number that looks like one.**
- [[Gotchas/2026-08-18 - A script importing across packages silently moves the whole dist]] — **read when `services/api` serves code that is hours old, or a route that plainly exists returns 404 while `nest build` exits 0 and prints nothing.** TypeScript infers `rootDir` as the common ancestor of every INPUT file, so one harness under `scripts/` importing `../../sentinel/src/execution/strike-candidates` (deliberately — asserting against a *copy* of the evaluator would assert nothing) pulled `services/sentinel` into the build, raised the ancestor from `services/api/src` to `services/`, and moved **every output**: `dist/main.js` -> `dist/api/src/main.js`, plus a whole `dist/sentinel/` tree. `package.json` still runs `node dist/main`, which still existed **as the stale leftover of the last correct build** — so the API booted, `/health` returned 200, and it served yesterday's code indefinitely. Every signal is green (build 0, `tsc --noEmit` clean, 912 tests pass), which is why the hunt goes to routing/guards/proxy, none of which are wrong. Two amplifiers: `nest build | tail` reports **`tail`'s** exit code (always 0 — redirect to a file instead), and a corrupt `dist/*.tsbuildinfo` then blocks emit even after the real fix, needing `tsc --incremental false` (420 files) to break the deadlock. Ten-second check: `ls -d services/api/dist/api services/api/dist/sentinel` (either exists -> rootDir moved) and `ls -la services/api/dist/main.js` (older than `src/` -> stale). Fix: `tsconfig.build.json` excludes `scripts` — **load-bearing, not tidy**; removing it to silence a future script type error silently reintroduces the whole failure. Found while recovering from the sibling `.next` failure the same day, whose cause was **running `next build` against an app whose `next dev` was live** — both own `.next` and the production layout desyncs the dev chunk manifest
- [[Gotchas/2026-08-18 - Sentinel telemetry sink is never installed]] — **read before trusting the admin Agents page, run history, or any AI-cost number, and before "fixing" an empty `AgentRun`.** `AgentRun`/`AgentActivity`/`AiCallLog` are **completely empty — zero rows, all systems**, not stale. Cause: `packages/ai-core` keeps ONE process-wide sink and `setTelemetrySink` has exactly one caller, `services/api`'s `TelemetryService` — but `services/sentinel` is a **separate process** and installs none, so every `runAgentRun`/`trackAgent`/`emitAgentActivity` in the orchestrator emits into a documented null sink. Easy to misdiagnose because the correlation ids are real and consistent *within* a request and nothing ever errors (the null check is silent by design) — the failure is visible only by counting rows. Does NOT break order → run traceability: `ExecutionIntent.sentinelRunId` stores the id directly (a plain reference, not an FK, because telemetry is pruned and an intent must outlive it), so only the enrichment is missing and `ExecutionTraceService` names both possible causes rather than asserting one. Fixing it needs an authenticated ingest endpoint plus a batching client sink in sentinel's bootstrap — platform observability with its own retention/backlog questions, not a line of wiring. **Do not** have sentinel write those tables via its own Prisma client: `services/api` owns them and a second writer puts pruning in two places
- [[Gotchas/2026-08-17 - Next dev _Cannot find module .NNN.js_ is a stale .next, not your code]] — **read before debugging a Next dev server that 500s every route, including /login.** `Cannot find module './193.js'` from `webpack-runtime.js` is a DESYNCED `.next` cache, never your source: the runtime loads server chunks by number from a manifest, and when the two disagree it asks for a file that is not on disk. Four checks settle it in a minute — does the OTHER app fail too (admin had zero changes and failed identically), does the named chunk exist on disk, does `tsc --noEmit` pass, do the tests pass. Cause on 2026-08-17: both dev servers alive **over 24 hours** through a day of edits plus a branch switch, a `git stash` that reverted 16 files, its `pop`, and a merge. Fix: `npm run dev:reset` (stop the servers first) — quarantines the caches by rename, never delete. Also closes the `.gitignore` gap that let two build trees into git: `.next/` with a trailing slash does not match `.next.prodbuild-aside-*`
- [[Gotchas/2026-08-17 - A boot-once credential plus fault-shaped-like-absence took Sentinel down]] — **read before touching `live-feed-server.ts`, `candle-market-data.provider.ts`, or any code that turns an upstream failure into a value.** Whole session lost, 76% failure on `/observe`, from ONE mechanism: the bridge read its Dhan token into a module-level `let` at boot, and Dhan's 24h cap is *regulatory*, so a process outliving a day is **guaranteed by arithmetic** to hold a dead credential with no path back to the renewed one (proof: bridge 18.4h uptime, `.env` renewed 20 min earlier, api+sentinel restarted and working, bridge not — **compare process start time against config mtime when one component misbehaves and its neighbours don't**). Every failure path then returned an empty *successful* answer, so a refused credential was reported as facts about the market: "the bridge is unreachable" (it answered in 30ms), "no backfilled candles exist" (1,627 rows existed, all outside the 5-day window), and "NIFTY has no live option chain" (Dhan returns 18 expiries) — because `if (status >= 400 && status < 500) return []` treats 401/429 the same as Dhan's genuine `DH-813 no-derivatives`. The self-contradicting UI message ("NIFTY has no chain… indices like NIFTY have one") is **the signature of this whole class**: the UI had no way to say "I could not find out". `process.env` is a boot snapshot and dotenv won't overwrite a set var, so recovery needed reading the **file**. Concurrency amplified it four ways, all measured: failures never cached (8 identical failing reads = 8 Dhan calls), no in-flight coalescing on the hottest route (50 concurrent = 50 calls), ~13 users saturate 5 req/s and *failing then cost more than succeeding*, and the shared 3.1s FIFO gave the 3rd–6th concurrent caller 6.2/9.4/12.5/15.6s against a fixed 4s abort — read downstream as "no option chain", so **user B was told NIFTY has no options because user A asked first**. Leaves the rule: **an absence is a fact about the world, a fault is a fact about us, and they must never share a representation.** Also: a missing timeout *defeats* a fallback rather than slowing it (a hung socket is not an error, so `try/catch` never fires — Anthropic had no `AbortSignal` at all, `/observe` max 54,984ms), and `AiCallLog` is 0 rows so no AI cost claim is verifiable. Isolation audit was clean — timeline/state keyed `userId::symbol::istDateKey`, the bridge holds no user identity — so these were contention bugs, not contamination. Full audit: `SENTINEL_ROOT_CAUSE_AND_PERMANENT_FIX.md`
- [[Gotchas/2026-08-12 - Nest DTOs must be declared above the controller]] — **read before adding a `@Body()`/`@Query()` DTO to any Nest controller.** A DTO class declared *below* its controller is still in its temporal dead zone when `emitDecoratorMetadata` evaluates `design:paramtypes` at class-definition time, so the API dies at import with `ReferenceError: Cannot access 'X' before initialization`. `tsc --noEmit` passes and all 281 tests pass — **no test instantiates the Nest context, so only actually starting the service catches it.** The same boot exposed a second trap: `AdminService` is provided twice (by `AdminModule` and directly by `ControlModule`, deliberately, to preserve the console's no-exports boundary), which only works while its constructor needs nothing but the `@Global` `PrismaService` — injecting a second service into it takes down the *control plane* at boot. Live in-memory state goes on the controller; `AdminService` stays Prisma-only
- [[Gotchas/2026-08-11 - Sentinel feed fabricated a CE direction on signals that had none]] — **Rule 2 class, read before touching `SafetyCard.tsx`, `extractSafetyFeed` or `sideInFocus`.** Four stacked defects made the feed claim Sentinel favoured *calls* on evidence that said the opposite: the CE/PE badge was recovered by substring-matching card prose and **defaulted to "CE CALL"** for anything not matched as PE (a bearish CPR breakdown got a bullish badge; "O**PE**N range" got PE PUT); a *neutral* bias was coerced to bullish, manufacturing a side out of the one case that should surface nothing; the four-condition `publication` gate was taken as a parameter and **never referenced**, silently reverting a documented decision while its long explanatory comment still sat above the body; and "progress" measured `spot − nearest ATM strike`, a rounding artifact bounded by half a strike step, so on NIFTY it could never leave ±25 and "invalidated" was unreachable. ## API
API integration notes — auth quirks, rate limits, payload shapes, gotchas specific to a third-party API.
- [[API/2026-08-16 - NSE public data (FII-DII, participant OI, breadth) — what Dhan cannot give you]] — **read before any institutional-data feature, before assuming the Dhan token covers a market-data gap, and before giving any agent outbound web access.** **FII/DII is not in Dhan and no token unlocks it** — DhanHQ v2's whole data surface is charts/optionchain/quotes/scrip-masters; a broker publishes what it can execute, an exchange publishes what the market did. NSE serves it free and keyless: `/api/fiidiiTradeReact` (cash), `fao_participant_oi_DDMMYYYY.csv` (Client/DII/FII/Pro contracts), and — the surprise — `/api/allIndices` carries **advances/declines**, the first real breadth this platform has had. Three things make it work: cookie priming (**the prime may 403 and still set usable cookies** — read the jar, ignore the status), a browser-shaped request with a matching Referer, and `getSetCookie()` not `get('set-cookie')`. When NSE refuses it serves an **HTML page with a 200**, so the symptom is `JSON.parse` failing. **The limitation that shapes every UI decision: cash flow and participant OI are END-OF-DAY with no intraday equivalent at any price** — asked at 11am Tuesday, this data is Monday's, so every figure travels with its session. Agent reach is a **closed named-dataset catalogue, never a URL** (`{ask}` never a destination, asserted by test): a caller-supplied URL fetched from inside the network is an SSRF primitive, and fetched page text is data-not-instruction — which is why `event-calendar` drops the company-authored `bm_desc`. Gotchas: `en-IN` uses **lakh grouping** (`2,02,235`); the CSV's headers carry trailing whitespace so match by trimmed name; never coerce `"-"` to 0; and in the assistant's judgement guard **`buy`/`sell` must NOT trigger refusal** (unlike `quotes.ts`) or "did DIIs sell yesterday" is declined because the number is about selling, while `will` must be unqualified. Unofficial surface, no SLA, ToS restricts automated access — mitigated by server-side-only + one shared cache; a data agreement is the durable answer
- [[API/2026-08-11 - Dhan Algo Strategies]] — **read before automating any order placement against Dhan.** The headline: **Dhan has no endpoint that returns algo strategies** — `algos.dhan.co` is a UI-only marketplace of third-party, exchange-approved algos with no API. What exists is one server-side rule engine (**Conditional Triggers**, `/v2/alerts/orders`, API v2.5) whose entire expressible strategy space is the cross-product of 21 fixed-period indicators × 9 operators × 4 timeframes — catalogued here as 14 named archetypes — plus the Tier-3 primitives (`/orders`, `/super/orders`, `/forever/orders`). Also: `algoId` is read-only Dhan attribution, not a strategy id you supply; the docs' lookback limits are more generous than this repo's measured behaviour; and two doc self-contradictions (`comparisonType` enum, a claimed "Exit All API" that no page documents).
