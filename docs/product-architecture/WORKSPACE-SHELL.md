# Workspace Shell — Dockable Workspace, Command Palette, Theme Engine, Notifications

Status: **implemented (frontend-only), Phase 1 Milestone 3.** Governed by [`TRADEW-OS.md`](TRADEW-OS.md) §1 ("one continuous operating system, not a set of pages") and extends [`WORKSPACE-CONTINUITY.md`](WORKSPACE-CONTINUITY.md), whose client-local implementation lives here. No backend integration in this milestone — see §6 for the migration path.

## 1. Scope decision, stated up front

"Dockable workspace" here means a **slot-based dock** — five zones (`left`, `main`, `auxA`, `auxB`, `right`) that panels move between, resize within, collapse, pin, close, and restore. It is **not** a free-floating, arbitrary-pixel-position window manager (that's a materially larger engineering scope — full multi-window docking like a native desktop app). Multi-monitor pop-out is intentionally **architecture only**: every panel carries a `detachable` flag and a disabled "Pop out" control, with no window-detach implementation, matching the milestone brief's own scoping for that item ("no implementation yet, only architecture support").

## 3. State ownership: one store, not scattered `useState`

Milestone 2's `AppFrame` held `collapsed`/`mobileOpen`/`aiOpen` as local component state. Milestone 3
migrated all of it into `workspaceStore` — this was necessary, not incidental: `sidebarCollapsed` is
part of Workspace Continuity's promised "remember sidebar state" (`WORKSPACE-CONTINUITY.md` §2), and
centralizing overlay state (`commandPaletteOpen`, `shortcutsHelpOpen`, `notificationCenterOpen`,
`aiDockOpen`, `mobileNavOpen`) is what lets a single Escape handler (`closeAllOverlays()`) close
whichever overlay is open, from anywhere. `Sidebar`, `TopBar`, and `FloatingAI` now read/write the
store directly instead of receiving props from `AppFrame` — `AppFrame` itself is a thin shell that
mounts the hydration + keyboard-shortcut hooks once and composes the top-level pieces.

## 4. Panels, layouts, and workspace tabs

- **Panel** (`PanelState`): `{ id, kind, slot, order, collapsed, pinned, visible, detachable }`. Closing
  sets `visible: false` (kept in the array, so `ClosedPanelsMenu` can restore it) — never removed.
- **Layout preset** (`LayoutPreset`): a named, full `PanelState[]` snapshot. Six built-ins — Scalping,
  Swing (the default/original M2 arrangement), Options, Learning, Research, Minimal — generated by
  `buildPresets()` from one base arrangement with targeted overrides, not six hand-written duplicates.
- **Workspace tab** (`WorkspaceTab`): `{ panels, leftWidth, rightWidth, mainHeightPct, selectedSymbol,
  watchlistTab, activeLayoutId, layoutDirty }`. Applying a layout preset replaces the ACTIVE tab's
  `panels` + resets its column/row sizes; a user's subsequent resize/move/collapse/close edits mark
  `layoutDirty` (shown as a dot next to the Layout menu label) until they re-apply a preset.
- Switching workspace tabs swaps the entire `panels`/sizing/symbol bundle — verified in the browser to
  be fully independent both directions (Workspace 2 defaults to Swing while Workspace 1 keeps a
  customized Options arrangement; switching back restores it exactly).

Moving a panel between zones is native HTML5 drag-and-drop, scoped to the small grip handle in
`DockControls` (not the whole panel card, so drag doesn't fight normal clicks/selection inside a
panel's body). Reordering within a zone has an explicit ▲▼ button pair — deliberately not drag-only,
so reordering is fully keyboard-operable (Milestone 3 §14 accessibility requirement).

## 5. Command Palette doubles as Global Search

The brief lists a Command Palette (§5) and Global Search (§6) as separate items. This implementation
unifies them into one overlay with a **modular provider registry**
(`lib/search/providers.ts`, `SEARCH_PROVIDERS: SearchProvider[]`) — the same pattern real command
palettes use (VS Code, Linear). Real providers today: navigation (from `nav-config.tsx`, so adding a
sidebar page automatically makes it searchable), stocks/indices (mock market data, deduplicated),
learning topics, and workspace commands (theme, sidebar, notifications, shortcuts, layout reset, new
tab). Five **stub providers** — Portfolio, Research, Sentinel, Knowledge, TradeW AI — each surface one
disabled "search coming soon" row, and only when the query plausibly targets that domain; this is the
literal fulfillment of "prepare modular providers, backend search can come later" (§6): swapping a stub
provider for a real one is a change to that provider's `search()` body, nothing else.

The top-bar search field is a **button styled as a search input**, not a live-typing `<input>` — it
opens the palette rather than trying to duplicate its own search logic. This was a deliberate fix
during implementation: an earlier version used a real `<input>` with an `onFocus` handler that blurred
itself and opened the palette, which is dishonest to both mouse and screen-reader users (a focusable
field that immediately un-focuses itself). A button that says what it does is the correct primitive.

## 6. Workspace Continuity — client-local implementation (interim)

`WORKSPACE-CONTINUITY.md` §3 specifies a server-owned `workspace_session` table. This milestone
explicitly excludes backend integration, so `workspaceStore`'s zustand `persist` middleware
(localStorage, key `tradew-workspace-v1`) is the **interim client-local implementation** of that same
contract — deliberately shaped close to the eventual server schema (open tabs, panel/layout state,
selected symbol, sidebar state, theme) so migrating is a transport change (swap localStorage reads/
writes for `services/api` calls), not a redesign. `partialize` excludes transient overlay booleans and
regenerated built-in layouts — only genuine continuity state persists.

**Hydration safety** — the store is created with `skipHydration: true` and manually rehydrated in a
`useEffect` (`useHydrateWorkspaceStore`, mounted once in `AppFrame`) rather than synchronously at
module load. Reading `localStorage` during store creation would make the very first client render
differ from the server-rendered HTML (a hydration-mismatch trap) since the module runs once during SSR
(no `window`) and once during the client's first paint. Deferring to `useEffect` guarantees the first
client render matches SSR exactly, then updates a moment later — the standard-safe pattern. The same
constraint required the store's very first default workspace tab to use a **fixed id** (`'tab-1'`)
rather than `Math.random()` — a random id would differ between the server and client's first render
and break React's reconciliation keys.

Verified end-to-end in the browser: theme, layout customization, and panel collapse/close state all
survived a hard reload with zero console errors and no visible flash.

## 7. Theme Engine

Three themes — dark (default), light, high-contrast — all defined as CSS custom-property sets in
`packages/ui/src/styles/tokens.css` (the high-contrast set is new this milestone: pure black/white,
saturated market-direction colors, ~21:1 body-text contrast). Nothing that consumes design tokens
needed to change to support the third theme.

**No-flash-on-load**: an inline `<script>` in `apps/web/src/app/layout.tsx`'s `<head>` reads the
persisted theme from `localStorage` and sets `data-theme` on `<html>` synchronously, before React
hydrates — the standard next-themes-style technique. `suppressHydrationWarning` on `<html>` is required
for this exact pattern (React would otherwise warn that its rendered attribute doesn't match what the
script already set in the DOM). Subsequent theme changes (via `ThemeMenu` or a command palette command)
apply through a small `useEffect` in `AppFrame` that syncs `theme` → `data-theme` on every store change.

## 8. Notification Center

One store-owned notification list (`NotificationItem[]`, seeded with mock data across all 7 brief
categories: trade, sentinel, learning, research, portfolio, broker, announcement) — read by three
surfaces that previously would have needed three copies: the top-bar bell's unread badge, the
`NotificationCenter` drawer (Ctrl-independent, opened from the bell), and the full `/notifications`
page. No backend yet; the shape matches what `services/notification`'s eventual fanout
(`N8N-WORKFLOWS.md`) will populate.

## 9. Keyboard shortcuts

Documented in `lib/shortcuts.ts` (source for `ShortcutsHelp`) and implemented in
`useKeyboardShortcuts.ts`. Every bound combo uses a modifier key (Ctrl/⌘), which is why the handler can
fire globally regardless of focus — a modifier+letter combo never types a character into a focused
field, unlike a bare key. Escape is the one bare-key binding and is safe everywhere. **Space is
deliberately not bound** — a global Space handler would break every button and text input on the page;
it's reserved as a placeholder for a possible future "quick preview" action, not wired to anything now.

## 11. Open items

- Cross-slot drag currently appends to the end of the target zone rather than inserting at a precise
  drop position — reordering after a cross-zone move uses the ▲▼ buttons. A precise-position drop
  indicator is a UX refinement, not a correctness gap.
- Multi-monitor pop-out (§1) has no implementation — only the `detachable` flag and a disabled control.
- Layout presets don't yet support user-defined custom presets (only the 6 built-ins) — the
  `LayoutPreset[]` array shape already supports appending user presets; wiring "Save current as…" is
  future work.
